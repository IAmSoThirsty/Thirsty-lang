## Finish this candidate

1. **Close the static typing increment.** Start with `tests/test_mutable_type_conformance.py` and `tests/test_value_choice_conformance.py`, then run the neighboring callable, constructor, cascade and iteration suites. At each declaration, return, argument and write, an operation on a known choice must be valid for every possible value. A fresh literal may take a compatible contextual type. A shared nested container keeps its writable element type after a shallow copy. Check successful same-type writes, scalar widening and existing diagnostic codes alongside rejection cases. Document what callers can rely on in the language specification.
2. **Resolve runtime mutation at typed boundaries.** Trace a single typed list and dictionary through aliases, function arguments and returns, a struct field, and standard-library mutation helpers. Specify how native values entering through an explicit `Any` boundary acquire and retain constraints. Cover direct and indirect writes, including nested values. Acceptance requires every supported write route to reject an incompatible value before changing the container, preserve alias identity for valid writes, and give a bounded result for deeply nested or cyclic values. Record the trusted host boundary separately.
3. **Qualify the combined tree.** Run the full suite with the repository's 90% coverage floor, Ruff, Black, mypy for Windows and Linux, and dependency checks. Compare checker diagnostics and runtime results for the same representative programs. Build the wheel and source distribution from the checkpoint in an isolated build directory, install the wheel in a fresh environment, and run the CLI plus an execution-limit and a mutable-container example outside the checkout. Regenerate the user manual and API docs against the final source, check PDF determinism, and record the commit, artifact hashes, commands, failures and platform skips. The earlier M4.1 result of 5,084 passing tests applies to its September snapshot. A fresh hosted Linux run depends on available Actions access or a separate Linux runner.
4. **Exercise the language as an application author.** Use the existing `src/utf/examples/data_report/` program as the first acceptance fixture. Run it from the installed CLI with a fixed input and expected output, then add cases for malformed input and a denied file operation. Extend the application corpus one workload at a time as described under M7 in the [development roadmap](../DEVELOPMENT_PLAN.md). Choose the next language feature from a concrete program that cannot yet be expressed or run reliably.

Execution quotas beyond M4.1, portable backend conformance, broader standard-library coverage, and package distribution each have separate acceptance criteria in M4–M7 of the roadmap. The immediate engineering deliverable is a tested mutable-value contract on the reference interpreter. A release version or publication decision follows candidate qualification.

The [November qualification record](LANGUAGE_DEVELOPMENT_QUALIFICATION_20261118.md) tracks completion, the installed application checks and the portable-backend fixtures.
